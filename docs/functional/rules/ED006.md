# ED006 — public-secret

**Requirement:** FR-RULE-ED006

| Item | Value |
|---|---|
| Milestone | M1.5 |
| Source | [PRD §11](../../prd.md#11-rules) |
| Explain text | [`rules.md`](../../rules.md) |

## Summary
A variable whose name says it is secret also carries a frontend prefix (`NEXT_PUBLIC_`, `VITE_`, …). Bundlers inline such variables into client JavaScript, so the secret ships to every browser.

## Fires when
A referenced **or** declared name meets both conditions:
- It starts with a configured frontend prefix.
- It contains `SECRET`, `PRIVATE`, `TOKEN`, `PASSWORD`, `PASSWD`, `CREDENTIAL`, or `KEY`.

**Exception:** names ending in `PUBLIC_KEY`, `PUBLISHABLE_KEY`, or `SITE_KEY` do not fire.

| Property | Value |
|---|---|
| Default severity | `error` |
| Locations reported | All references **and** declarations of that name |

## Matching details
- The prefix match is case-sensitive and uses `startsWith`, against `frontendPrefixes`.
- The keyword match is case-sensitive and checks the part **after** the prefix.

> **Open question:** should the keyword match be a substring or a `_`-separated token? Substring matching makes `KEY` match `NEXT_PUBLIC_KEYBOARD_LAYOUT` and `MONKEY_ID`. *Proposal:* match keywords as whole `_`-delimited tokens or token prefixes (`KEY`, `KEYS`, `APIKEY`). Until Rahul decides, implement the PRD's literal substring semantics and record the false positives in the benchmark.

## Grouping
There is one finding per name.

## Message template
`<NAME> looks secret but has frontend prefix <PREFIX>, so it is bundled into client code`

## Fix template
`Rename without <PREFIX> and read it server-side; rotate the secret if it was ever deployed`

## Examples

**Fires**
```tsx
// src/app/page.tsx
fetch(url, { headers: { Authorization: process.env.NEXT_PUBLIC_ADMIN_TOKEN } });
```
With `frontendPrefixes: [NEXT_PUBLIC_]`, the result is `ED006 error NEXT_PUBLIC_ADMIN_TOKEN src/app/page.tsx:2`.

**Does not fire**

| Name | Reason |
|---|---|
| `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` | Exception suffix |
| `VITE_RECAPTCHA_SITE_KEY` | Exception suffix |
| `VITE_API_URL` | No keyword |
| `ADMIN_TOKEN` | No prefix (server-side) |

## Interactions

| Aspect | Behaviour |
|---|---|
| Ignore | Names in the merged ignore list never fire |
| Suppression | Per location: code `// envdrift-ignore ED006`, or dotenv `# envdrift-ignore ED006` |
| Prefixes | No prefixes configured means ED006 cannot fire. `init` detects prefixes from dependencies. |
| `via` | Applies to `process.env`, `import.meta.env` and accessor references alike |

## Required tests (`packages/core/test/rules/ED006.test.ts`)
1. **Positive:** `ED006 fires for prefixed names containing each secret keyword, in code and in declarations`.
2. **Negative:** `ED006 does not fire for PUBLIC_KEY/PUBLISHABLE_KEY/SITE_KEY suffixes or unprefixed names`.
3. **Suppression:** `ED006 is dropped when all locations carry envdrift-ignore ED006`.

The fixture `vite-app` covers `VITE_` end to end.
